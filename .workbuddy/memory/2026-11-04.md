### 最重要的结论：这是设计约束与产品目标冲突，不是性能退化

现行实现把「一段手势跨多张」**明确当作要防住的缺陷**钉住了：

- `README.md`「一次手势最多换一张」：想连续翻多张必须抬手再滑；
- `tools/check_wheel_swipe.mjs` 文件头四条硬性纪律第 1 条「一段连续的流最多结算
  一次，甩得再远也不连翻」，并有断言「一次长距离横滑（推 + 惯性尾巴）只翻一张」；
- `ui/js/viewer.js::attachGestures()` 注释：`wheelState` 交接是为了防止「一次甩动
  会因为一路达标而连翻好几张」；
- `README.md` 343~358 行专门论证固定冷却、峰值比例解锁都是踩过的坑，「连翻」
  在历史上是 bug。

所以用户想要的「连续快速滑动跨多张」正是现有检查器判为失败的行为。改进属于
**语义/架构级改动**，调阈值或「多等一会儿」解决不了，且必须同步改检查器契约
与 README 设计章节，否则会「代码对了、检查器红」。

### 三个结构性来源

1. **惯性尾巴被主动丢弃**：`lockWheelSwipe()` 置 `locked` 后，后续 wheel 增量只记账、
   不跟随、不结算（`gestures.js` 950 行注释），直到静默 ≥65ms / 反向 ≥60px /
   1200ms 上限才解锁；README 自己写了 macOS 惯性尾巴能持续 1s+。
2. **三槽轨道把跟手夹死在一屏**：`wheelFollowOffset` 超过一屏走橡皮筋，
   `WHEEL_OVERSCROLL_RUBBER` 注释「再拖也没有第四个槽可显示」——手指继续推，
   画面停住，跨多张在结构上不可能。
3. **每翻一张都重建 + 排队**：`go()` → `attachGestures()` detach/new 并手工交接
   `wheelSwipe`；动画期间 `enabled=false`，`settleWheelSwipe()` 碰到就每 60ms
   重试最多 600ms → 连续快滑时结算排队，这正是「延迟累积」。
   另外只预取目标 ±1 一张原图，跨张时后续图未预热，结算帧撞解码。
   `claimTrack()` 那段注释已承认「连续切几张之后就不跟手、按下去要等一下」，
   之前只修了「WAAPI 关键帧吞掉跟手」这一层，没动上面三条。

### 对照依据（已查证）

- Apple 支持《Mac 上"照片"中的触控板手势》：查看单张照片时双指向左/右轻扫
  = 上一张/下一张。
- Apple《Handling Trackpad Events》：`NSScrollWheel` 有 `phase` 与
  `momentumPhase`；**惯性滚动 = 用户已停止物理滑动后硬件仍继续发滚轮事件**，
  有 Began/Changed/Ended 生命周期；**滚动/轻扫手势一旦开始就锁定到结束**；
  惯性阶段事件路由到手势开始时的视图。
  ⟹ 原生体验是「一条连续滚动流，位移连续映射内容位置，惯性持续驱动，速度衰减后
  吸附到某一张」；PicShow 是「离散翻页 + 每段结算 + 丢弃惯性 + 三槽窗口」。

### 硬约束 / 风险

Web 的 wheel **不暴露系统阶段标记**，只能靠静默推断流结束（当前 65ms/600ms），
这是与原生最本质的能力差，也是所有推断误差的根源。设备差异（deltaMode、
「滚动方向：自然」、非标准方向属性、Magic Mouse、尾巴长度）会放大误差。
其它入口（单指拖拽、键盘/按钮、胶片条）共用 `go()` 与三槽 rebalance，语义改动
容易带偏它们的手感。真实惯性流与跟手观感只能真机 A/B 验收。

`check_wheel_swipe.mjs` 的「一次一张」契约而不是绕过它。

## 决策（本轮）：wheel 横滑「一次一张」体验退化 → 完整回滚到连续滚动流

用户报告上一次「一段连续流只切一张」造成体验退化，要求按六维核对后二选一：
能明确改善就提交改进实现，否则完整回滚到改动前行为。最终**只采用一种确定方案**。

### 六维评估

- **切换方向**：映射正确未退化，但只在流末按**最终净位移**定向，中途掉头的
  往返互相抵消 → 该切不切。
- **触发阈值**：「跨满一屏」这个与行程成比例的换页阈值被删，只剩流末
  `22% / 峰值速度`；且 `swipeX` 被夹到 `viewW - 1`，`far` 几乎恒真 →
  距离/速度不再影响结果。
- **灵敏度**：累计夹在不足一屏后，后续输入不再产生视觉变化，轻推与全力甩
  同结果，「画面停住 / 不跟手」回归。
- **连续滑动稳定性**：每次结算都要等 65ms 静默 + `go()` 收尾，快速连滑的
  延迟按次累积。
- **漏触 / 误触**：漏触增加（反向抵消、惯性尾巴 ≥65ms 空隙被切成两段）；
  误触减少是唯一收益，代价覆盖其余五项。
- **其他预览交互**：纵向 / 放大态平移 / 单指拖拽 / 键盘 / 胶片条不受影响。

**定案：完整回滚（方案 B）。** 与上一轮评估结论一致：Web wheel 不暴露
`phase` / `momentumPhase`，「一次物理手势」没有可靠边界；靠调静默窗口、速度闸
或冷却做「改进」要么把延迟与锁带回来、要么吞掉下一段手势，而本机浏览器探针
起不来、真机惯性无法验收，**无法可靠验证优于改动前**。按用户规则取唯一确定方案。

## 本轮：目标图第一帧就位（槽位永不空白）

用户要求：wheel 横滑一开始目标图就要从对应侧边缘立即、连续进视口，全程不露
空白 / 背景 / 空白帧 / 跳变；方向、惯性、首尾阻尼、其他交互都不许动。

### 四个真实成因（都不是「阈值没调好」）

1. `fill()` 原地给底图 `setSrc()`：先抹掉旧像素，再等一次 `img://` 请求 + 解码，
   恰好在起手 / 连续换槽那一两帧露成背景。
2. 跟手期间画的是**缩略图** `thumbUrl()`，但静止期 `preloadNeighbors()` 只预热
   原图 —— 预热了错资源。
3. `prefetchNeighbor()` 排在 `rebalance()` **之后**：它要填的正是「再下一张」那个
   槽，等填完才预热，每次推进都注定错过自己那轮的已解码节点。
4. 越界槽被显式清空，而首尾 90px 阻尼会把这一小条拉进视口 = 主动露黑边。

另有一处隐蔽的供给死角：`takeDecoded()` 取走即出池、`preload()` 又按 URL 缓存
promise —— **反向滑回一张早就取过的图时，池里永远不会有第二个节点**。所以光有
「已解码图片池」不够，必须有慢路径新建独立节点、`decode()` 完才交付。

### 改动

- `api.js`：新增 `DECODE_WAIT_MS` / `decodedImage(src)`（池命中即取；池空则新建
  独立 `Image()` 等 `decode()`，失败 / 超时交 `null`，调用方保留旧像素）。
- `viewer.js`：`NEIGHBOR_READY_MS = OPEN_MS`，`open()` 把
  `Promise.all([leftReady, rightReady])` 接在 FLIP 之后、开放手势之前（与转场
  并行、有上限）；`openGen` 世代号作废旧开场回调；`advanceBy()` 把方向预热
  `PREFETCH_RUN` 与反向 1 张移到 `rebalance()` 之前；`fill()` 改走
  `swapSlotImage()` / `installSlotImage()` 原子替换，`__swapGen` 挡后发先至；
  越界槽用当前图缩略图保底、`__shown` 与 `__index` 分开记；`resetSlots()`
