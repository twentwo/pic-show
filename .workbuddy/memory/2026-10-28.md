# 2026-10-28

## 横滑切换：一次手势只准翻一张（修「滑得远一点就连翻两张」）

现象：Mac 触控板上一次长横滑跳两张。先在 `ui/probe.html` 加了复现用例 `17.2g`
（40 帧 × 25px 连推 + 衰减尾巴，帧间隔 16ms），改代码之前实测 `1 → 3`。

根因（`ui/js/gestures.js`）：
* `wheelTailOver()` 里那条「单次增量 ≥ 本次峰值 0.8」的出口 —— 一次持续推力中
  每帧增量本来就在峰值附近，380ms 硬锁一过就把还在推的事件当成「又推了一把」；
* 另外原「反向 ≥ 10px」那条符号判据也是反的（`dir = -sign(dx)`，判反向应用
  `sign(dx) === sign(s.dir)`），会把同方向的持续推力误读成反向。

改动：
* 删掉 `WHEEL_RESTART_RATIO / WHEEL_RESTART_MIN_PX / peak`；解锁只留三条：
  380ms 硬锁 → 反向累积行程 ≥ `WHEEL_REVERSE_TRAVEL=60` → 静默 ≥ 180ms（+1200ms 兜底上限）；
* 新增 `trackWheelReverse()`（反向累积，同向事件清零），`lockWheelSwipe()` 顺带清 `rev`；
* 鼠标滚轮不受影响：每格之间天然有静默，落在「静默解锁」那条上。
* 单指拖拽侧：`onPointerDown` 加 `enabled` 闸门（切图/展开/关闭动画期间不接受手势，
  否则 `go()` 因 `switching` 返回而 track 卡在半张图）；松手判定抽成
  `decideSwipeRelease()`，位移(22%视口宽) 或 速度(0.45px/ms 且 ≥28px) 命中即置
  `swipeFired` 消费凭证，其余一律回弹到 0。

新增 `tools/check_wheel_swipe.mjs`（Node + 可控时钟的状态机回归，已进 `npm run check`）。

### 教训
`dir`（+1=下一张）与 `dx`（屏幕坐标，向左为负）符号相反，`dir = -sign(dx)`；
任何用这两个量比较方向的地方都要先想清楚符号。这次是靠把 `handleWheelHorizontal`
拉到 Node 里单跑（临时脚本）才一眼看出来的 —— 浏览器探针只报「多翻了一张」，看不出哪条判据。

## 横滑二次优化：跟手与响应（修「双指横滑不跟手、切换延迟」）

现象：功能能用，但画面和手指不同步、松手后要等一下才动。

四个真因（`ui/js/gestures.js`）：
1. **轴向拿第一个事件定生死**：`dx=3 / dy=4` 这种起手噪声下 `|dx| > 1.7·|dy|` 不成立，
   代码落到 `else if (dy !== 0) axis='y'`，整段横滑被当成缩放丢掉 → 用户得再滑一次。
   「第一次滑不动」就是它。改为**累积** ≥ `WHEEL_AXIS_LOCK_PX=10` 后再按两轴总和判。
2. **结算窗口 120ms**：触控板尾巴 8~16ms 一发，连丢 4 帧就说明停了 → 改成 65ms。
3. **只在流停后才结算**：加了「意图明确就当场走」两条出口 —— 累计 ≥48px 且当前速度
   >1.1px/ms（甩）、或累计 ≥ 半张图。甩的门槛特意高于单指的 0.45，否则中速滑动
   （0.4~0.8 很常见）全被当甩，只跟 3% 就飞走。
4. **回弹动画盖住跟手**：Web Animations 关键帧优先级高于内联样式，`animateTrackTo()`
   没跑完时写 `style.transform` 是无效的 → 跟手前先 `if (this.anim) this.cancelAnim()`。

性能侧：一段手势只量一次视口宽（`s.viewW`，避免每事件强制同步布局）；跟手路径不再
逐事件 `emit()`；wheel 的 `onUserActivity` 改走 `noteMotion()` 节流；`dt` 夹在 8~64ms
（8ms = 120Hz 帧距，滤掉同帧双事件算出的虚高速度）。

首帧：方向一确定就 `onSwipeIntent` → `viewer.prefetchNeighbor()`；`api.preload()` 在
`onload` 后显式 `img.decode()`（只下载不解码，位图解码仍会落在收尾动画第一帧）。
收尾动画时长按剩余距离缩放（`110~300ms`，`SWIPE` 的 `fromSwipe`）。

验证：`npm run probe` 202/202 ×2 尺寸（新增 17.1b 跟手度、17.1f 流内结算、17.1g 轴向噪声）；
`check_wheel_swipe.mjs` 30 条（含「甩的延迟为负 = 提前结算」「慢拖窗口 60~70ms」）；
`check_trackpad.mjs` 重写为结构断言（原来那版还停留在 `wheelTailOver` 时代，12 条假失败）。

### 教训
* 探针里 `wheel({deltaX: 正})` = 手指向左 = 下一张，而内部 `dx` 是负的；写跟手度断言时
  累计量要跟着取负，否则「误差 102px」这种假失败会以为是逻辑错。
* 同一毫秒内连发两个 wheel 事件会被算成超高速度，测试里补 `sleep(40)` 即可；
  但真机也要防（`dt` 下限 8ms）。

## 横滑三次优化：连续切换后失同步（修「切几张之后就不跟手」）

现象：连续切两三张之后再滑，画面不动、要等一下才跳；单次切换时正常。

两个真因，都是「状态跨切换没清理」：
1. **切图收尾动画不归 gestures 管**：`animateTrack()` 跑在 `track` 上（WAAPI），句柄存在
   `viewer.trackAnim`，而手势只知道自己的 `this.anim`。动画没播完时写 `style.transform`
   被关键帧盖住 → 那一段跟手全被吞。用户几乎总在上一次收尾里再次起手，所以「连续切
   之后」才明显。
2. **65~600ms 的窗口不清状态**：只有 >600ms 才算换手势，抬手 100ms 后再滑会沿用上一段
   的 `x` / `peakV` / `intent`（以及新加的 `base`），既不再接管新动画，峰值速度还会让
   慢拖被判成甩。

改动：
* `viewer.claimTrack()`：读 `getComputedStyle(track).transform` 的 `m41` → `anim.cancel()`
  → `rebalance()` + `trackOffset = -slotWidth()` → `switching=false` / `g.enabled=true`，
  返回 `visual - trackOffset`；`attachGestures` 把它传给手势。
* `wheelSwipe.base`：接管偏移，跟手写 `base + x`；判定仍只看 `x`（base 不参与阈值）。
  `lockWheelSwipe` / `reboundWheelSwipe` / `attachGestures`（跨实例交接）都要把 base 作废。
* `go()` / `jumpTo()` 加 `switchGen` 世代号：接管让旧 `await` 提前回来时，认得出
  「我不是当前那一次」，不误改新实例的闸门。
* `handleWheelHorizontal` 开头：`sincePrev >= WHEEL_GESTURE_END_MS` 就软重置
  `x/base/vx/peakV/intent/rev`，只留 `axis` 与 `viewW`。

验证：`npm run probe` 207/207 ×2（新增 17.14a~e 接管连续性）；`check_wheel_swipe.mjs`
36 条（新增第 14~18 组：接管偏移语义、回弹归零、只接管一次、抬手 100ms 重新接管、
峰值不跨段）；`check_trackpad.mjs` 新增 7 条结构断言；`npm run check` 全绿。

### 教训
* **探针把 `Element.prototype.animate` 换成了「立即完成」的替身**，所以「动画覆盖内联
  样式」这条真实行为在探针里永远测不到 —— 前两轮「全绿但真机不跟手」就是这个原因。
  这类「浏览器语义 vs 替身」的差异要手工造现场（设 `viewer.trackAnim = {playState:
  'running', cancel()}` + 直接写 inline transform）。
* 排查时打印每轮的 `from / got / swipeX / base / trackOffset`，一眼看出第 2 轮 `base=0`
  没接管 —— 比只看「最大误差 787px」有用得多。

## 横滑四次优化：回弹被打断丢位移（「前一段位移丢失、不跟手」）

现象：连续横滑切多张后再次起手，画面像丢了一截、明显迟滞。（承接上一轮的接管修复）

根因：`reboundWheelSwipe()` 把 `wheelSwipe.base` 写死成 `0`，而回弹（`animateTrackTo`
200ms）是 WAAPI 关键帧 —— `cancelAnim()` 的瞬间视觉掉回内联值，也就是归位后的 `0`。
于是「回弹还没播完就再滑一次」时，那段没走完的位移整段消失、画面往回跳一截。
`animateTrackTo` 一上来就把终值写进内联样式，所以丢的就是**整段未走完的位移**。

改动（两处，都在 `ui/js/gestures.js`）：
* `reboundWheelSwipe()`：`base` 由 `0` 改为 `null`（回弹的**终点**才是 0）。
* 跟手分支：掐 `this.anim` **之前**先 `trackVisualOffset()`（读 computed transform 减
  `trackBase`）拿到回弹中途的位置；`claimTrack()` 有返回值就用它，否则用这个值。

`check_wheel_swipe.mjs` 第 19 组（慢推 36px → 回弹 → 中途再滑）反向验证过：退回旧写法
会报「swipeX=-20 期望 -46.1」，即 26px 回跳。

### 教训
* **端到端仿真比单测更快定位**：把真实 `Gestures` + 一个 100 行的 viewer/轨道替身
  （`visual` = 有动画取插值否则取内联）放进 Node 跑，逐事件打印
  `dx / x / base / swipeX / vis before→after / err`，三个场景（正常连切、动画未播完就
  再起手、回弹打断）一次跑完，直接量化「跟手误差」和「结算延迟」。
  写这类替身要注意两点：`style.transform` 的写入必须回写到视觉值、`getComputedStyle` /
  `DOMMatrixReadOnly` 要自己补（Node 里没有）。
* 造「慢拖不达标」的用例时先算速度：`30px/40ms = 0.75px/ms` 已经越过单指松手的
  `0.45` 阈值，会直接翻页 —— 要真正的慢推（12px/60ms = 0.2）。
