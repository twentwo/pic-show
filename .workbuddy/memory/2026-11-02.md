# 2026-11-02

## 「退出预览后窗口停在最大化」第三轮：找到真凶并根治

前两轮都在治「运行时切装饰」（tao 的 `saved_style` 覆盖链），治完仍不生效。
这一轮换了个做法：**先不读自己的代码，直接用 Swift + AppKit 写一个独立几何
探针，证明平台层到底行不行**。

### 真凶：进全屏前写过一次几何

AppKit 还原窗口用的是**进入全屏前那一帧**。`commands::prepare_launch_window`
趁窗口还藏着做了 `set_size(整块屏)` + `set_position(0,0)`，而**仅仅把 frame
设成屏幕尺寸，macOS 就当场判定它 `zoomed=YES`** —— 于是 AppKit 从此把「最大化」
当成还原目标，退出时一丝不差地还原回去。它没出错，它还原的是我们写脏的那一帧。

探针实测（1200×800 窗口往返一次原生全屏）：

| 场景 | 进全屏前 | 退出后 |
| --- | --- | --- |
| 全程不写几何 | 1200×801 @(360,127) | 1200×801 ✅ |
| 同上 + 复刻 tao 的 `restore_state_from_fullscreen` 补偿 | 同上 | 同上（早退）✅ |
| 进全屏前摆到整块屏 | 1920×1055 **zoomed=YES** | 1920×1055 ❌ |

顺带把 tao 0.37.2 的底摸清了：`windowDidExitFullScreen:` →
`restore_state_from_fullscreen()` 会**无条件** `set_maximized(shared_state.maximized)`，
那份记账我们从不写、恒为 false。它平时早退，但在「全屏前已 zoom」时会
`zoom(nil)` 把窗口拉小 —— 一颗定时炸弹，靠不动装饰与几何才让它永远走不到。

### 采用的方案：几何终身只读

`prepare_launch_window` 现在**不摆尺寸、不点亮、不设焦点**，趁窗口还藏着直接
`set_fullscreen(true)`。实测 AppKit 会在切进全屏时自己把窗口显示出来
（`windowDidEnterFullScreen` 时 visible=Y），亮起来的直接是整屏画布 —— 既没有
1200×800 那一帧，也没有「先摆大再全屏」的污染。

顺带省掉了原本为消闪烁准备的 alpha 方案（那需要 NSWindow 指针，Tauri 2.12.5
核心不暴露 `ns_window()`）。焦点交给前端 `handOverFocus()`。

风险与兜底：
- tao 的 `set_fullscreen` 要先取 `current_monitor()`，隐藏窗口拿不到就会静默
  return —— **实测 `NSWindow.screen()` 在隐藏态返回 1920×1080（非 nil）**，且
  old_screen == new_screen，不会触发 `set_frame_top_left_point`。
- AppKit 万一没顺手点亮：前端 `waitFor(viewportFillsScreen)` 超时后发现视口没
  铺满，补一次 `showWindow()`；`lib.rs` 里还有 3 秒全局兜底。两道都只补可见性。

### 交付

- 删除：`commands.rs` 的 `set_size`/`set_position`、`model.rs` 的
  `LaunchWindowRect`、`launch.js` 的 `launchWindowRect()`。
- 新增：`tools/appkit_geometry.swift`（可复跑的系统级证据，`--tao` / `--presize`
  / `--hidden` 三个开关）。
- 检查器新增**几何铁律**：Rust 侧出现 `set_size` / `set_position` /
  `set_maximized` / `set_decorations` 直接失败。这是把三轮失败钉死的关键 ——
  之前的检查只禁了装饰，没禁几何。另加一条守 `tauri.conf.json` 的初始尺寸必须
  是普通尺寸（改成 maximized 也会永久停在最大化，而且没有代码看着像有嫌疑）。

### 验证

- 反向验证：把删掉的两行塞回去 → `test:restore` 报 2 处、`test:boot` 报 1 处。
- 真机 E2E（起 `tools/serve.js` + debug 二进制 + 图片路径）：窗口
  `1920×1080 @ (0,0)` onScreen=Y，标题 `128x128@2x.png — PicShow`，日志里
  「前端取走打开请求」→ 切全屏，全程无 `set_size`。
  **纯 `cargo build` 缺 `custom-protocol` 会去连 devUrl，前端跑不起来
  —— 真机验证必须同时起 `tools/serve.js`。**
- 全量：`check:all` 全绿（静态 13 项、退出探针 71/71、画廊 234/234×2），
  `cargo check` 零告警。

### 教训

同一个现象连续三轮没修好，是因为每一轮都在**自己代码里找**那一笔覆盖，而
真正的机制（AppKit 还原的是「全屏前那一帧」）在平台层。先用一个独立探针把
平台行为测成事实，再去读自己的代码 —— 顺序反了就会一直在错的地方改。

## 第四轮：方案 B —— 两个物理窗口（用户拍板）

A′（几何终身只读）上线后用户反馈「还是没修复」。结论：只要图片墙与预览共用
同一个窗口，就必然存在一段「既是浏览态、又是全屏态」的生命周期，那期间发生
的所有写入都要经过 AppKit 那套 `saved_style` / `zoomed` 记账，而我们的补偿与
它的写入排在同一条 `DispatchQueue.main` FIFO 上 —— **纯竞态，sleep 只能改变输
的概率**。

### 结构

```
main 窗口   index.html + main.js          从不进全屏、几何从未被写过
viewer 窗口 viewer.html + viewer-main.js  拥有全屏；关闭只是 hide()
```

- viewer 在 `tauri.conf.json` 里**静态声明**（不是动态 create）：常驻，避免每次
  点图都付一次 webview 初始化。
- 图片墙那条窗口一次全屏都没进过 ⇒ 根本不存在「退出预览要还原成什么」。还原
  不是做对了，是**没发生**。

### 跨窗口状态（两个 webview 无共享 JS 上下文）

| 方向 | 内容 | 通道 |
| --- | --- | --- |
| 主 → 预览 | 有序图片集合、索引、来源矩形、immersive | `open_viewer`（待取件）+ `picshow://viewer-goto`（事件），前端 `viewer_boot` / 监听认领 |
| 预览 → 主 | 关闭时用户在看第几张 | `close_viewer` → `picshow://viewer-closed` |

- `AppState::current` 存**有序**列表（registry 是 HashMap，无序）。
- 冷启动竞态用与 `take_launch_target` 同一个套路：先挂监听 → `viewer_listening`
  → 再取待取件。
- **几何一律走物理像素的屏幕坐标**：主窗口 `+outer_position × dpr`，预览窗口
  `−outer_position ÷ dpr`。用物理像素是为了绕开 `scale_factor()`（阻塞等回执的
  getter，在命令里问会自锁）。
- 关闭动画的落点改为**开场时记下的那一格**（`viewer.originRect`）—— 预览窗口里
  没有网格 DOM，不能再现问。

### 几个「删掉而不是改」的点

- `Viewer` 的 `onBeforeClose` / `prepareBackstage` / `BACKSTAGE_MS` 整段删除：
  没有形态需要还，留着就是一个没人会挂的死钩子。
- 双出口修好：`finishClose` 曾同时调 `onClosed`（immersive 时 exitApp）和
  `onExit`（exitOnClose 时 exitApp）⇒ 一次关闭退出两次。现在 `onClosed` 是唯一
  出口，「要不要退出」由会话侧决定，`Viewer` 不认识 immersive。
- CSS 的 `body.is-immersive .viewer { inset:0 }` 也删了（`.viewer` 本身已是
  inset:0）。

### 检查器

- 删 `check_stage_restore.mjs`，新增 **`check_window_split.mjs`**（几何铁律 +
  全屏只切在 VIEWER_LABEL 上 + 前端不许有形态记账）。
- 反向验证（把禁掉的写法塞回去，看检查器是否报）：
  `set_size` in open_viewer / `maximize()` 兜底 in viewer_ready /
  `MAIN_LABEL` + `set_fullscreen` / main.js 里的 `wantedStage` —— **四条全中**，
  还原后复绿。
- 教训（可复用）：「某个名字不该再出现」这类断言必须**剥掉注释再扫源码**，
  否则解释「为什么删它」的注释会让它永远假警 —— 于是注释越详实检查越吵，
  最后人只能把注释删掉，那是最坏结果。`check_preview_entry.mjs` 也补了同一个
  `stripComments`。

### 探针的连带改造（踩坑记录）

- `ui/probe.html` 以前只 fetch `index.html`；现在要**两个页面都拼进来**
  （`adopt(wallDoc); adopt(viewerDoc)`）。
- **搬走节点之后原文档的 `getElementById` 就查不到了** —— 取证必须在 adopt
  **之前**。
- `Viewer` 构造改成 `{ root, onError, onClosed }`（不再收 grid）；入口一律
  `openLaunch(i, rect)`；`zoomStart(options)`（旧签名 `zoomStart(thumbRect, opts)`
  已废）。
- 19 节改为包 `viewer.playClose` 来拍「收摊前那一刻」的状态（旧 `onBeforeClose`
  钩子没了）。
- 结果：静态全绿 + 退出探针 60/60 + 画廊探针 **235/235 × 2**（之前 134/136，
  因为运行时抛错后面大段没跑到）。

## 真机 E2E 抓到一个「全绿状态下的致命缺陷」：能力声明漏了 viewer 窗口

静态、探针、cargo check 全绿之后，用 `PICSHOW_DEBUG=1` 起 debug 二进制
（**必须同时起 `node tools/serve.js`**）跑打开方式路径，日志里赫然：

```
[picshow][前端] event.listen not allowed on window "viewer" ...
allowed on: [windows: "main", URL: local]
```

**Tauri 2 的能力是按 window 授权的**：`capabilities/default.json` 里
`"windows": ["main"]`，于是新加的 `viewer` 窗口连 `core:event:default` 都拿不到
—— 预览永远收不到会话，整条跨窗口链路是死的。

修复：新建 `src-tauri/capabilities/viewer.json`（最小权限：`core:event:default`
+ `core:window:allow-start-dragging`，后者是页面里 `.viewer-bar` 的拖动区要的）。
**这类缺陷没有一种自动化手段能在本地抓到，真机 E2E 是唯一手段。**

顺带钉住它：`check_boot.mjs` 加了一组「每条窗口都被某条能力覆盖」（读
`tauri.conf.json` 的 label 与 capabilities 目录求差集）。反向验证：把
`"windows": ["viewer"]` 改成 `["nobody"]` → 3 条断言全红。

### 另一个 E2E 观察（判定为环境 artifact，不是缺陷）

日志里 `预览窗口就绪：全屏=true` 之后，到焦点那一步变成 `fullscreen=false
focused=false`。对照组：常规启动（不带文件）时主窗口也是
`focused=false visible=true` —— 说明这个沙箱根本不给应用激活，AppKit 因此不做
Space 过场。真机上未验证，代码侧没有可疑点（读 tao 0.37.2 确认：`set_fullscreen`
先立刻把 `shared_state.fullscreen` 置上，`toggleFullScreen` 才排队，所以
is_fullscreen 立刻为真是预期）。

E2E 现在留下的永久痕迹（仅 `PICSHOW_DEBUG=1`）：预览窗口就绪（全屏 + 原点）、
焦点请求（visible / fullscreen / focused）、主窗口点亮（focused / visible）。

## 第四轮：分家之后的两个后遗症（残留 Space + 开场动画生硬）

### 缺陷一：退出预览后 macOS 残留一个「PicShow」桌面

`close_viewer` 只 `hide()`。而 macOS 原生全屏开的那个桌面是**由窗口的全屏态撑
着**的：`orderOut:` 只是把窗口从屏幕上摘走，全屏态还在，桌面就还在。

修法：**让位 = 先退出全屏 → 等转场播完 → 再 hide → 叫回主窗口**
（`commands::release_viewer`，后台线程）。三条退出路径都要走：正常关闭、
`exit_app`、`on_window_event` 拦下预览窗口的 `CloseRequested`（`prevent_close`
+ `eval("window.__picshowRequestClose?.()")` 转给前端走正常关闭）、
`RunEvent::ExitRequested` 兜底。**中途 `hide()` 会把转场掐断，桌面照样留下。**

**关键教训：`is_fullscreen()` 不能当「转场播完」的信号。** tao 在
`set_fullscreen()` 里请求发出的那一刻就把 `shared_state.fullscreen` 写成了目标
值，调用完立刻再问已经是 false。真正可信的是**窗口框架**（`inner_size()`）：
- 主判据 = 回到 `viewer_ready` 在进全屏**之前**记下的常规尺寸；
- 兜底 = 尺寸先离开全屏值、再连续两次不变；
- 提前返回 = 尺寸从来没变过 → 那次全屏压根没生效（沙箱/远程桌面拿不到激活时
  必现），一帧都不用等，否则白等满 1.6s。

真机日志可以确认这一点：`预览窗口常规尺寸：2400×1600` → `就绪：内容区=2400×1600`
（进全屏后尺寸没变 = AppKit 没有真的执行）。

还加了世代号（`AppState::bump_viewer_epoch`）：「关掉又立刻点下一张」时，上一
次让位还在等转场，照做会把刚点亮的窗口又藏掉。

### 优化二：跨窗口开场动画对不上那一格

三处各自让起点偏掉一块，都是「编译得过、跑得出，只是从错的地方长出来」：

| 坑 | 修法 |
| --- | --- |
| `view()` 返回的是 stage 尺寸、原点 (0,0)，而来源矩形是**视口坐标**；stage 给顶栏让了 `--chrome-top`、给胶片条让了 `--strip-h` → 起点整体偏一个顶栏高度 | `localRect()` 先把视口坐标折成 stage 坐标 |
| `mapBoxToRect` 按**宽度**等比缩放，但网格那一格是 `object-fit: cover` **裁**出来的 → 起点框比那一格矮一截/窄一截 | 改 **cover**（两方向各算一次取大值） |
| cover 之后画面溢出那一格 | 转场期间给 stage 加 `clip-path: inset()`，从那一格动画到 `inset(0)` |

另外两处闪：`fill: 'backwards'` 填满动画开跑前那一帧（否则先闪一帧全尺寸）；
`viewer.preload()` 在切全屏那段等待里**并行**取回首图（`img.decode()`，上限
400ms），避免「空框长大再突然填上」。等布局也从「拿 `window.screen` 猜」换成
后端回报的真实尺寸（`viewer_ready` 现在返回 `ViewerFrame`，`viewportMatches`）。

时长/缓动：跨窗口这次变形单独用 `MORPH_EASE = cubic-bezier(.32,.72,0,1)`、
`OPEN_MS = 380`（`EASE` 那条前段猛冲，用在「从缩略图长到整屏」就是「啪」地弹开）。

### 验证

- 静态全绿；退出探针 60/60；画廊探针 **241/241 × 2**。
- 反向验证：让位里去掉 `exit_viewer_fullscreen` → 报；`mapBoxToRect` 退回按宽度
  → 报（静态 + 几何单测）。
- 真机 E2E 只能跑到「打开预览」这一段（沙箱不给应用激活，`osascript` 发按键被
  -10004 权限拒绝），Space 回收与动画观感必须人工按 README 第七节第 9~19 项验。

## 修复：退出预览后残留一个空白窗口盖在图片墙上

上一轮的 Space 残留修完（`exit_viewer_fullscreen` 先退出全屏），露出下一层：
退出预览后**一个空白的 PicShow 窗口叠在图片墙窗口上，再也不消失**。它跟图片墙
尺寸位置一模一样（都是 1200×800 居中，严丝合缝），内容已被 `finishClose()`
清空，看着就是一块空白。

### 平台级实测（tools/appkit_fullscreen_exit.swift，新探针）

```text
[  4.079] toggleFullScreen → 退出
[  4.113] frame 落到终值 1200×801     ← 旧代码的判据在这一刻成立
[  4.664] didExit                     ← 转场真正播完，晚 552ms
```

| 模式 | 结果 |
| --- | --- |
| 一量到 frame 到终值就 `orderOut:`（旧代码） | ✗ 窗口仍然可见 |
| 同上 + 400ms | ✗ 仍然可见（补不上 530ms 的差） |
| 等 `windowDidExitFullScreen:`（现在） | ✓ 彻底移除 |

**`NSWindow.frame` 比转场播完早约 530ms 落到终值** —— 旧代码把 `orderOut:` 掐在
了转场进行中，AppKit 的收尾随即把窗口拉回来。差不是固定值，**靠「多等一会儿」
补不上**，只能等 AppKit 自己的信号。

### 改动

- `macos.rs::native_fullscreen()`（新）：在主线程上问 `NSApp.windows()` 里有没有
  窗口的 `styleMask` 带 `.fullScreen`。**这是 AppKit 的记账，不是 tao 的** ——
  tao 的 `is_fullscreen()` 在 `set_fullscreen()` 请求发出那一刻就写成了目标值。
  已在主线程就直接问（`ExitRequested` 是同步跑在主线程上的，派发 + 等回执必自
  锁）；问不到返回 `None`，**不乐观猜**。
- `commands.rs::exit_viewer_fullscreen()`：主判据换成上面那个；它说「还在」时
  **尺寸判据一律不采信**（`Some(true) => continue`）；尺寸降为兜底。
- `commands.rs::hide_viewer()`（新）：「请求 + 确认」。反复查 `is_visible()`，
  **连续两次**看不见才算数（`is_visible()` 同步且和 `hide()` 排同一队列，拿到
  答案时前面那条 `hide()` 一定执行过了）；**只在还看得见时才重发 `hide()`**（每
  轮都无脑 `orderOut:` 会掐断还在播的转场）；期间 epoch 变了就停手（否则把刚点
  亮的预览一起摁掉）。
- `release_viewer()`：顺序钉死为「确认窗口消失 → 才 `reveal_main_window()`」——
  后者同步执行 `[NSApp activateIgnoringOtherApps:]`，会把整个应用的窗口一起提到
  前台。

### 验证

- 静态全绿（含 `cargo check` 零告警）；退出探针 60/60。
- 反向验证：让位里塞回裸 `hide()` → 报；去掉 `Some(true) => continue` → 报。
- 画廊探针在这台机器上起不了浏览器（SIGTERM）。**本轮改动是纯 Rust**，不受影响。
- 真机验收按 README 第七节第 16~20 项。

## 修复：预览窗口残留空白窗口 —— 改成「退出即销毁、进入按需重建」

用户第三次报同一个现象，并明确要求「彻底销毁（而非隐藏、清空内容或仅移除画
布）」、所有退出路径一致、不重复创建窗口实例。上一轮那套「退出全屏 → 等
`didExit` → 确认式 hide」在真机上仍留下可手动关闭的空白窗口 —— **方向本身就不
对**：只要窗口对象还活着、且经历「整屏缩回 1200×800」的转场，那一帧空白就在。

### 平台级实测（扩展 tools/appkit_fullscreen_exit.swift）

新增 `--close-in-fullscreen` 模式：全屏稳定时直接 `win.close()`（≈ Tauri
`destroy()`），不 toggle、不播退出转场。结果：

    [  4.05] win.close()
    [  4.13] didExit                ← AppKit 自己回收桌面
    windows 1 → 0；windowWillClose 收到；全程 sawNormalVisible = false
    ✓ 窗口从层级移除、没有常规尺寸的空白窗口帧

对照 `--at-frame`：frame 终值比 didExit 早 526ms，窗口被转场收尾拉回来（✗）。
**直接销毁绕开了整个转场难题**，还顺带解决 Space 残留。
