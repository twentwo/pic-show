# 2026-10-27

## 修复「右键 → 打开方式」启动的两个问题（主界面闪现 + 键盘焦点）

### 问题 1：主界面一闪而过
根因不是顺序写反，而是**判定时机太晚 + 平台差异**：

* Windows / Linux 的关联打开把路径放进 argv → 可以早判；
* macOS（访达「打开方式」）走 Apple Event（`RunEvent::Opened`），要等事件循环
  转起来，可能与首屏加载赛跑 → 前端取不到待取件就直接点亮主界面。

改动：
* `lib.rs::run()` 第一行就 `argv_targets()`，赶在 `build()`（创建窗口 + webview
  开始加载）之前判定；
* `AppState::started`（进程启动时刻）+ 新命令 `launch_decision_budget`
  （预算 300ms，**从进程启动时刻起算**，不是「从现在起再等 N ms」）→ 首屏慢的
  机器来问时预算已耗尽，常规启动零额外延迟；
* `commands::window_ready` 加闸门：`was_launched() && has_pending_launch()` 时
  直接 return，拒绝点亮（后端兜底，防任何路径画主界面）；
* `main.js`：`claimLaunch()` 保证事件 / 待取件两条通道只处理一次；`enterImmersive()`
  若 `windowShown === false`（冷启动）转走 `bootLaunch()`，否则动画播给隐身窗口。

**真机才暴露的 bug**：`boot()` 里把「事件通道已接管」的判断写在了
「自己取到的 pending」之前 —— `claimLaunch()` 认领成功就置 `launchHandled`，
导致自己取到的那份也被当成别人处理过的，直接 return，主界面被 3 秒兜底点亮。
已改为先判 pending 再判 launchHandled。

### 问题 2：键盘焦点要等图片落地
三层原因叠加（缺一个都复现不出来）：
1. 窗口 `visible:false` 隐藏启动 → tao 的 `set_focus` 第一条判断就是
   `isVisible`，隐藏窗口上要焦点被平台直接忽略（tao-0.37 macos/window.rs:652）；
2. macOS 的 `maximize()` 是一次 zoom，会把刚抢到的 key window 让出去；
3. 图片未落地时按键落在空画面上。

改动：`prepare_launch_window` 顺序固定 show → maximize → set_focus；新增
`focus_window` 命令 + `Viewer#focusWhenReady()`（底图/原图谁先到算谁，4s 超时兜底）
+ `Viewer#focusView()`（`#viewer` 加 `tabindex="-1"`，CSS 去掉 outline）；
`main.js::handOverFocus()` 排在启动分支最后；网格焦点只在非沉浸式分支给。

## 双指手势状态机审计与修复（JsGestures）

### 结论（先定性）
* 当前**没有**独立的「双指横滑切图」——该功能早已回退，只剩注释化石
  （`gestures.js` 里写在 updatePinch 上方的 `updateTwoFinger`）。
* 手指数 ≥ 2 **无条件**进 pinch：不判轴向、无阈值、无方向要求。所以「双指横向
  移动」就是捏合的一种形态：间距变了→缩放，没变→平移。
* 因此双指下拉**不会**关闭、双指横移**不会**翻页；要关闭/翻页必须用单指。

### 修的两个真 bug（都是状态共用导致的）
1. **残留 swipeX**：单指横滑中途加第二根手指 → pinch 全程不写 swipeX，那截偏移
   一直挂在轨道上（实测停在 -1632 vs 基准 -1432，即半张图错位），只能靠再翻一页
   （`go()` 清）或改窗口尺寸（`refit()` 清）自愈。
   修法：`beginPinch()` 入口处 `if (swipeX !== 0) animateTrackTo(0, 260, EASE_SOFT)`。
2. **抬手基准跳变**：`onPointerUp` 2→1 分支原本调 `beginPinch()`，但它对「只剩一根」
   是 `pts.length < 2 → return` 的空操作 → `start` 与 `mode` 停在捏合那一刻。若活的
   不是建立 start 的那根手指，dx 里混进两指间距 → 实测 rawX 从 -10 跳到 +170（200px）。
   修法：新增 `releasePinch()`，以剩余手指重建 `start/last/vel`，`mode='pan'`、
   `pinch=null`。

### 判定 `mode='pan'` 而非 `'undecided'` 的理由
捏合刚结束时手指带余速，缩回适配尺寸后随手一划就被判成翻页太容易。

### 探针
新增第 16 节（13 项：静态正则 4 + 行为 9），两种尺寸各 **172/172**。
负向验证：删 swipeX 归位 → 16.1c/16.3c/16.3d FAIL；退回空跑 beginPinch →
16.1d/16.4a/16.4b FAIL（-10 → 170）。

### 探针编写踩坑
* `viewer.open()` / `go()` 会**重建** Gestures 实例 → 别缓存 `viewer.g`，用 Proxy 或每次重取；
* open 期间 `g.enabled=false`（防 FLIP 与手势打架）约 200ms，手工派发事件前要把它打开；
* 读回 `track.style.transform` 会被浏览器序列化成 `...px, 0px, 0px`，别拿 `0` 去比串，取数值比。

## 触控板双指横向滑动切换图片（仅 macOS）

### 结论落地
走 **wheel 的 deltaX**，不是 pinch 分支：Mac 多指手势在系统里就被翻译成
wheel / ctrl+wheel / click，DOM 里永远凑不出第二个 pointerId，所以
`pointers.size >= 2` 那条 pinch 分支在触控板上不可达（只活在真触摸屏上）。
范围限定：仅 macOS 触控板 + 全屏看图。

### 改动
* `gestures.js`：`onWheel` 改为「先做轴向归属再决定谁处理」；新增
  `handleWheelHorizontal` / `panByWheelX` / `resetWheelSwipe` / `freshWheelSwipe`
  / `wheelSign`；`normalizeWheel(event, axis)` 支持横向（DOM_DELTA_PAGE 按轴取宽高）。
  阈值：`WHEEL_AXIS_RATIO=1.7`、`GAP=600ms`、`DEADZONE=8`、`TRAVEL=12`、
  `COOLDOWN=320`（≥ SWITCH_MS=300）、`EDGE_DEADZONE=48`。
* `viewer.js`：注册 `onWheelSwipe` → `go(direction)`（到首尾由 go 自己 nudge）；
  attachGestures 用 `wheelState: previous?.wheelSwipe` 把一次手势的状态跨实例交接。
* 新增 `tools/check_trackpad.mjs`（18 项），接入 `npm run check`。

### 踩到并修掉的真 bug（值得记住的写法）
`const s = this.wheelSwipe; if (gap) this.resetWheelSwipe();` —— reset 会换新对象，
`s` 仍指向旧的 → 每个事件都从 0 累加，跨事件阈值永远攒不够。必须：
`if (gap) this.resetWheelSwipe(); const s = this.wheelSwipe;`。
探针 17.1e/f 与检查器都会拦这个写法。

### 方向约定（别搞反）
经过推导并一致化：自然滚动下 **正的 deltaX = 手指向左 = 内容向左 = 下一张**
（与已有单指 `dx<0 → direction+1` 同义）；关闭「自然」后符号整台翻转，靠
`webkitDirectionInvertedFromDevice`（WebKit 专有，必须 feature-detect）归一化，
保证「向左划 = 下一张」在两种设置下一致。

### 验证
* 探针第 17 节 14 项，桌面/窄屏各 **194/194**；
* 9 组负向验证（去边缘死区 / 去冷却 / 状态不交接 / 去 ctrl 互斥 / 去放大态平移 /
  去方向归一化 / 去单图兜底 / 去抖动阈值 / 后端打开 allowsBackForward）均精确 FAIL；
* **真机未能端到端验证**：用 Swift + CGEvent 合成滚动事件投递给运行中的 PicShow，
  连纵向滚轮缩放也没反应 → macOS 不允许这种跨进程合成投递（也与 osascript 缺
  Automation 权限一致）。但真机已确认 app 正常渲染（pic2.png、2/3、标题栏在），
  说明新代码没有语法/运行期错误。

## 触控板双指横滑：方向反了 + 一次滑动连翻多张（真机反馈修复）

### 两个症状的根因
1. **方向反**：`handleWheelHorizontal` 里 `direction = Math.sign(t.x)`，漏了负号。
   单指横滑的写法是 `dx < 0 ? 1 : -1`（手指向左 = 下一张），wheel 路径的累积量
   同样是屏幕坐标系下的手势位移（向左为负），必须用 `-Math.sign(t.x)` 才一致。
   ✅ 不是 wheelSign 写反 —— 中途我一度把 wheelSign 整体翻掉，结果纵向滚轮缩放
   跟着反了（探针「滚轮放大生效」FAIL），据此反推出 wheelSign 原本正确：它与
   纵向共用同一系数才对（详见下）。
2. **连翻**：原来是固定 `320ms` 冷却。macOS 惯性尾巴能持续 1s+，冷却一到尾巴就把
   累积重新攒满 → 一次轻甩翻好几张。

### 本机环境（重要）
`defaults read NSGlobalDomain com.apple.swipescrolldirection` = **1** → 用户
**关闭了 macOS「自然滚动」**（非出厂默认）。所以在这台机器上 DOM delta 恰好反向。

### deltaX 符号的正确推导（以后别再绕）
DOM 约定固定：`deltaX > 0` = 向右滚动 = **内容向左**；`deltaY > 0` = 内容向上。
- 自然滚动**开**（默认）：内容跟手 → 内容向左 ⟹ 手指向左 → 要取反才是手势方向；
- 自然滚动**关**（本机）：内容反向 → 内容向左 ⟹ 手指向右 → DOM delta 数值即手势方向。
纵横两轴共用同一系数（`wheelSign`），因此纵向手感不变（手指向上 = 放大）。
`webkitDirectionInvertedFromDevice === true` ⟺ 自然滚动已启用（AppKit 已按偏好反转过
一次）；Apple 文档 + SO 一致。非标准，Chromium 恒 false，只按值判断。

### 修复：一次手势只翻一张
`cooldownUntil` 固定时间戳 → 换成 `locked` 状态机，解锁看**这一串 wheel 是否真的结束**：
`wheelTailOver()` 四条出口 —— 下限 380ms(≥SWITCH_MS 300) / 静默≥180ms 且幅度≥8px /
反向≥10px / 幅度≥0.8×本次峰值（**鼠标滚轮靠这条做到一格一张**）/ 硬上限 1200ms。
`peak` 在锁定期**不更新**（清掉会让重启判据恒真）。
关键点：`lockWheelSwipe()` 必须在 `onWheelSwipe` **之前**调用（先落锁再翻页）。

### 顺带修正的一处
`handleWheelHorizontal` 提到 `enabled` 闸门**之前**：`go()` 在切图动画 300ms 里把
手势冻结，但尾巴没停 —— 那段时间不记账会让同一串尾巴被误判成「早停息过」。
代价是 `enabled` 要作为参数传进去（canFire），否则会在动画里翻页。

### 探针编写教训（headless 环境）
- `Element.prototype.animate` 是替身 → 300ms 转场被压缩到 ~40ms。要覆盖「动画期间」
  必须手动置 `viewer.g.enabled = false` 把那段时间还原出来。
- `webkitDirectionInvertedFromDevice` 在 headless Chromium 恒 false → 会被当成
  「关闭自然滚动」的机器。wheel helper 默认补 true 来模拟 macOS 默认；17.9 单独
  构造缺失版本覆盖另一种设置。
- 想用「是否连翻」来区分实现差异很不可靠（解锁后还要凑够位移才翻）。改断言完成时
  直接观测可测量的事实（preventDefault 是否发生、时间戳是否推进）。
